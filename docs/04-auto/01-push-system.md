# 定时推送系统：从n8n迁移到crontab的踩坑实录

## 8.1 我想要什么

你每天早上醒来，想第一时间看到当天的早报——天气怎么样、GitHub上有啥值得看的、三门峡本地有没有大新闻。

晚上吃完饭，想看今天的微博热搜、抖音热搜、百度热搜，看看大家都在聊什么。

睡前呢？瞅一眼今天的国际金价和国内金价，看看行情。

这就是**定时推送系统**。说白了就是：到点了，机器人自动把整理好的信息推到我手机上。不需要我手动操作，不考验我的记忆力，一切按时自动完成。

## 8.2 第一版：用n8n

n8n是个自动化工具，拖拖拽拽就能搭工作流，看着挺美的。我一口气搞了7个工作流：

| 推送内容 | 时间 |
|---------|------|
| 🌅 早报 | 每天早上7:00 |
| 🔥 热搜 | 每天晚上19:00 |
| 💰 金价 | 每天晚上20:30 |
| 📊 复盘 | 每天晚上23:00 |
| 🏢 圈层情报 | 每天12:00和21:00 |
| 🎬 每周影视 | 每周四22:00 |
| 📈 每周报告 | 每周五20:00 |

听起来挺健全的对吧？

### 踩坑1：Code节点不能读文件

n8n 2.20.11版本的Code节点禁止使用 `require('fs')` 来读取本地文件。我所有工作流的第一行代码都是读本地JSON数据，结果一跑就崩。

**修复方案：** 搞了个本地数据服务器（Python写的，HTTP接口），工作流用HTTP Request节点去请求数据，不走文件读取了。

### 踩坑2：URL里不能用变量

我在HTTP Request节点的URL里写 `http://localhost/data?date=$today`，心想这很合理吧？结果n8n告诉我：URL字段不支持JS表达式，$today 就是个普通字符串。

**修复方案：** 改成在Code节点里用 `fetch()` 请求数据，代码里拼URL，想怎么拼就怎么拼。

### 踩坑3：定时器自己停了

以上两个坑好歹都有解决办法。最致命的是第三个坑——

跑了一周后，某天我突然意识到：好像好几天没收到推送了？去n8n一看，工作流的Active状态还在，但定时触发器就是不触发了。查询日志，啥也没有，就静默罢工了。

这大概是n8n cron调度器的bug。重启n8n之后能恢复，但过几天又停了。自动化的核心就是"不需要我管"，结果我得天天盯着它有没有死，那还自动化个啥？

**修复方案：** 彻底放弃n8n，迁移到Linux系统自带的crontab。

## 8.3 第二版：系统crontab + Python直推

换方案之后，架构变得极其清爽：

```
采集环节：
  collector_daemon.py（持续运行，每30-60分钟采集一轮）
    ├─ 新闻采集器（天气/GitHub/三门峡新闻）
    ├─ 热搜采集器（微博/抖音/百度）
    ├─ 金价采集器（国际+国内）
    └─ 圈层情报采集器（HN/Reddit/V2EX）

中转环节：
  data_server.py（Python HTTP服务器，端口18888）
  采集器把数据存到文件 → data_server提供HTTP接口

推送环节（7个crontab定时任务）：
  0 7 * * *     早报推送
  0 19 * * *    热搜推送
  30 20 * * *   金价推送
  0 23 * * *    复盘推送
  0 12,21 * * * 圈层情报
  0 22 * * 4    每周影视
  0 20 * * 5    每周报告
```

采集和推送彻底分开。采集器是个常驻进程，按固定节奏干活。推送就是7条crontab，到点执行一个Python脚本，去data_server取数据，然后推送到Telegram。

crontab是Linux内核级的定时器，几十年历史了，不可能自己停。

## 8.4 踩坑：data_server缓存旧数据

迁移到crontab之后一切正常，但有一天发现金价显示为0。

排查半天，发现data_server一直返回的是前一天失败的采集数据——上一轮采集因为网络问题没成功，data_server没有清空旧数据，就一直返回那个脏数据。

**修复方案：** 手动触发一次采集器，生成最新数据。后续可以加一个数据时间戳校验，超过一定时间的数据直接返回"暂无数据"而不是返回过期数据。

## 8.5 给你的建议

- **n8n适合做短流程，别依赖它的定时器。** 如果你非要用n8n，可以在n8n外另搞一个crontab定期调用n8n的Webhook来触发，而不是让n8n自己计时。

- **采集和推送分开。** 这是血的教训换来的。采集是采集，推送是推送，不要混在一个流程里。采集失败不影响推送逻辑，推送失败也不影响继续采集。

- **数据走文件/HTTP中转，比数据库简单得多。** 不需要MySQL、不需要Redis。Python写个简单的HTTP服务器，采集器往文件里写JSON，推送端通过HTTP读JSON。够用、好排查、好维护。

- **系统crontab是最可靠的定时方案，没有之一。** crontab从Unix诞生就有，死了几万次都没出过问题。定时任务这种基础功能，越底层越可靠。

最后送一句话：**别把自动化搞得太复杂。** 复杂意味着脆弱，而脆弱会让你的自动化变成另一种负担。
